# HDL Final Project

## 1. Project Objective and Motivation

The objective is to move a pipelined RISC-V processor from behavioural simulation to physical hardware on the PYNQ-Z2 board and to verify it using a hardware-in-the-loop (HIL) methodology. Instead of a Verilog testbench, a Python script running on the board’s ARM processor (Processing System, PS) acts as the testbench: it loads the program and data into shared memory, releases reset on the RISC-V core implemented in the Programmable Logic (PL), waits for completion, and checks the results.

## 2. Architectural Overview

The system has two main parts:

- **Processing System (PS):** The ARM Cortex-A9 core running Linux and a Jupyter environment. It executes the verification script, which uses the PYNQ Overlay to load a bitstream, access AXI BRAM controllers and GPIO via memory-mapped I/O, and thus control and observe the PL.
- **Programmable Logic (PL):** The RISC-V core (custom RTL), two Block RAM (BRAM) instances, AXI BRAM controllers, AXI interconnect, and GPIO. The core fetches instructions from one BRAM and reads/writes data from/to the other; the same BRAMs are accessible by the PS for loading and verification.

The RISC-V core is a five-stage pipeline (fetch, decode, execute, memory, write-back) implementing a subset of RV32I. It exposes BRAM-compatible master interfaces for instruction and data memory and is packaged as an IP for integration in the Vivado block design. Reset is driven by the PS via GPIO so that the host can ensure the program and data are loaded before the core starts executing.

## 3. Memory Layout

The design uses a **dual-BRAM** layout (separate instruction and data memories):

- **I-ROM (instruction memory):** The PS writes the program; the PL (RISC-V core) only reads. The core drives the instruction BRAM address (PC) and receives the instruction word each cycle.
- **D-RAM (data memory):** Both PS and PL read and write. The PS injects the test array and reads back the sorted result and the DONE flag; the core performs load/store operations during execution.

## 4. Verification Workflow

The intended workflow is:

1. **Bitstream and overlay:** Load the generated bitstream (e.g. `risc_v_wrapper.bit`) via PYNQ’s Overlay so that the PL is configured and the RISC-V core is in reset.
2. **Memory injection:** Write the contents of the program hex file into the instruction BRAM; write 32 signed integers into the data BRAM; clear the status flag at 0x1FFC.
3. **Execution:** Release reset via GPIO; the core runs from PC = 0.
4. **Polling:** Read the status flag at 0x1FFC repeatedly until the magic value (0xCAFEBABE) is read or a timeout is reached.
5. **Result validation:** If the magic value was read, read the 32 words of the data array from the data BRAM and compare them to the golden sorted sequence; report success or list mismatches.

The verification script is intended to run in a Jupyter Notebook on the PYNQ-Z2 (e.g. `verify.ipynb`) and uses the same constants and logic as the standalone Python script where applicable. A separate validation script (`scripts/validate_e2e_flow.py`) checks that the hex file and script conventions (instruction count, presence of the DONE write sequence) are consistent without requiring hardware.

## 5. Repository Structure

- **`Hardware_design/`**

  - RTL and block design for the PL.
  - **`RISC-V_core_IP/`:** The RISC-V core adapted for FPGA integration: source files (pipeline, decoder, ALU, register file, hazard unit, pipeline registers, sign-extension), IP packaging (component.xml, TCL), and Vivado project. This core has no internal memory; it drives BRAM interface signals (clock, enable, address, write enable, write data, read data) for separate instruction and data BRAMs.
  - **`RISC-V_core_old/`:** Simulation-oriented version of the core with internal instruction and data memory modules, used for Verilog testbenches (minimal DONE test, E2E flow test, hazard tests, bubble-sort test) and for generating/checking hex programs.
  - **`system_wrapper.v`:** Top-level wrapper for the block design (ZYNQ PS, AXI interconnect, BRAM controllers, BRAM, GPIO, RISC-V IP).

- **`Software/`**

  - **`python_code/`:** Verification script (`verify.py`) and Jupyter Notebook (`verify.ipynb`) for running on the PYNQ-Z2. They load the bitstream, discover BRAM controllers and GPIO, inject instructions and data, release reset, poll the DONE flag, and validate the sorted array.
  - **`RISC-V_code/`:** Assembly source (`Bubble_sort.S`) and hex file (`Bubble_sort.hex`) for the 32-integer bubble sort program. The program writes the magic number to the status address when sorting is complete.

- **`Bitstream_Hardware_handoff/`**

  - Generated hardware handoff (e.g. `risc_v_wrapper.hwh`) and, when produced, the bitstream file for programming the PL. The bitstream is typically generated by Vivado from the block design and placed here for use by the notebook.

- **`scripts/`**
  - **`validate_e2e_flow.py`:** Checks that the hex file loads correctly (comment stripping, hex parsing) and contains the expected instruction count and DONE write sequence (store of magic number at end of program). Run from the repository root; does not require hardware or RTL simulation.
